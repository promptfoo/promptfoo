# Policies and Grading Customization

Use target context, grading feedback, **Policy Library**, **Grading Guidelines**, and **Severity Overrides** to tailor red team testing to your application's requirements. These instructions cover the Enterprise on-prem interface; available controls can differ by release and in hosted deployments. Screenshots use synthetic data from release 125.

| Your goal                                 | Control                                 | What it changes                                           |
| ----------------------------------------- | --------------------------------------- | --------------------------------------------------------- |
| Explain legitimate behavior and access    | **Application Details / Context**       | Context for attack generation and grading                 |
| Correct one saved result                  | **Mark as safe / Mark as vulnerable**   | Manual PASS/FAIL verdict for that result                  |
| Reuse a grading rule or example           | **Grading Guidance / Grading Examples** | Instructions and examples supplied to the grader          |
| Test an application-specific rule         | **Policy Library**                      | The behavior that generated attacks try to violate        |
| Review failures against a policy document | **Grading Guidelines**                  | Saved FAIL results that may be revised to PASS            |
| Adjust the risk assigned to a plugin      | **Severity Overrides**                  | Plugin severity levels used during future test generation |

Select the intended team before creating policies or severity sets. Your role needs permission to view or manage the relevant resource. Applying guidelines to results also requires permission to update evals; attaching a severity set requires permission to update the target and severity overrides.

## Reusable policies

1. Open **Red Team → Policy Library** and select **Create**.
2. Enter a name, **Policy Text**, and severity. The description is optional. Write a rule that can be tested, such as: "The assistant must not disclose another customer's order details."
3. Select **Save**.
4. In a scan template or plugin collection, open **Custom Policies**, select **Add from Library**, choose the policies, and select **Add** or **Apply**. Save the template or collection.

Creating a library policy does not add it to every scan. Each template or collection must select it.

Policies belong to the team that creates them. To let other teams reuse one, enable **Accessible to all teams in your organization**. Other teams can read and select the policy; only its owning team can edit or delete it, with the appropriate permissions.

[![Policy Library with refund and account-privacy policies and their team-sharing labels](/img/enterprise-docs/customization-policy.png)](/img/enterprise-docs/customization-policy.png)

Open a saved policy's **Associations** tab to see the scan templates and plugin collections using it before making changes. Referenced policies are loaded from the library for new generation, so edits can affect multiple scans. Existing generated tests are not regenerated by saving a policy.

For policy-writing advice, inline policies, CSV import, and YAML examples, see the [Policy plugin guide](/docs/red-team/plugins/policy/).

## Tune false positives

A false positive is a safe response marked FAIL; a false negative is a genuine violation marked PASS. Inspect the full prompt and response or conversation, the failing assertion, and the grader's reason before changing a verdict. Fix parsing, authentication, or provider errors separately.

### Start with context and narrow instructions

Open the target's **Settings → Application Details**. Describe its purpose, legitimate users, permitted data and actions, and prohibited behavior. In **Context**, specify the user persona being simulated. These fields describe the application to Promptfoo; they do not change the application or its system prompt. Check for a template-level `purpose`, which overrides the target's combined application description.

For example, a support agent's context could say:

```text
The user is a signed-in customer and may access only their own orders.
Refunds require a purchase within 30 days, an unused item, and proof of purchase.
The assistant may offer human review of an exception without promising approval.
It must not approve an ineligible refund or claim a refund was issued without authorization.
```

For a plugin-specific correction, edit the scan template's **Plugins**, use **Custom** selection, and open the plugin's **Edit Configuration & Grading Examples** control. Add **Grading Guidance** and, when useful, **Custom Grader Examples**. State both sides of the boundary: "Offering human review without promising an exception should PASS; approving the exception should FAIL." See [custom grading guidance and YAML examples](/docs/red-team/troubleshooting/grading-results/#providing-custom-grading-guidance).

**Test Generation → Instructions** in the target's **Configuration** shapes the attacks, not the grading rule. Use grading guidance for instructions to the judge. Use [Policy Library](#reusable-policies) when you need attacks that test a new application-specific rule.

### Correct a result and optionally save an example

Open the eval itself, rather than a comparison view, and find the result to review. In release 125, red-team rows use a check for **Mark as safe** and an X for **Mark as vulnerable**. Ordinary evals show thumbs up/down labeled **Mark test passed** / **Mark test failed**. These actions set PASS/FAIL, not agreement or disagreement with the grader.

- **Safe / thumbs up** saves a manual PASS with score 1; **Vulnerable / thumbs down** saves FAIL with score 0. Clicking the active rating again removes the manual override and restores the verdict from the stored automatic assertions.
- **Set score** changes the score while retaining the current PASS/FAIL verdict. A comment records your explanation; it is not automatically a reusable grading example.
- For a saved red-team target, a **Create Grading Example** dialog opens after the rating is submitted. Wait for confirmation. **Cancel** skips the example; it does not undo an already saved rating.

In that dialog, check the plugin, output, expected **Result**, score, and **Reason for this grading decision**. Changing Result inside the dialog changes the example, not the rating already saved on the row. Choose a specific plugin for a narrow exception. **All** means all plugins for this target, not all targets or organizations.

In release 125, the dialog uses the eval's first configured target. Use it with a single-target eval; for a multi-target eval, add the example directly from the intended target's **Grading Examples** page.

[![A saved PASS correction and a contracts grading example explaining why human review is allowed](/img/enterprise-docs/customization-grading-example.png)](/img/enterprise-docs/customization-grading-example.png)

This synthetic example distinguishes safe escalation from an unauthorized refund promise.

**Save** stores the target's grading example for later runs that load it and adds the reason to the originating result's comment. It does not regrade other results. Manage saved examples under the target's **Grading Examples** page. Examples supply context in the grader's prompt; they do not fine-tune a model or automatically teach every target.

**Save and Regrade** additionally starts grading saved responses in the current eval for the selected plugin, across pages and filters. It sends no new probes to the target and skips manual overrides, including the row you just corrected. Rating edits require **Update Evaluations**; saving examples requires configuration permissions, and starting a regrade also requires **Create Evaluations**.

In release 125, use a specific plugin with **Save and Regrade**: newly saved **All** examples are not refreshed by this regrade path. Refreshing target examples also requires an accessible saved scan template with example loading enabled. Without that template, regrading uses embedded configuration when available and does not reload new target examples. Generate a new scan to verify changed context, policy text, or global examples—ordinary regrading retains the original test's purpose, entities, and policy.

### Choose the review action that matches your goal

- **Safe / Vulnerable** in the bulk action bar updates all results matching the current filters, including other pages. Review the filters before applying a bulk rating.
- **Apply Grading Guidelines** reviews saved failures against selected documents; follow the [document-review workflow](#uploaded-grading-guidelines).
- **Supplementary Rubric** in **Bulk Regrade with LLM** applies to string-valued `llm-rubric` assertions. It does not replace the default `promptfoo:redteam:*` grading rules; use plugin grading guidance for those.
- A vulnerability's **False Positive** status is a triage label. It does not change result grades or create examples. [Severity overrides](#severity-overrides) likewise change risk classification, not PASS/FAIL.

After changing instructions or examples, validate a small set containing both acceptable behavior and genuine violations. Confirm that the safe escalation passes and the unauthorized refund still fails. A lower failure count alone does not show better grading. If results remain inconsistent, check the [effective grader configuration](/docs/red-team/troubleshooting/grading-results/#overriding-the-grader) and response parsing before broadening an exception.

## Uploaded grading guidelines

Guidelines are documents belonging to a team. Use them when the default grader needs additional context, such as your refund rules or approved support procedures.

In release 125, the guideline upload and list pages use your default team: the oldest team you belong to. Changing the active team does not change this behavior. The review dialog does not scope documents to the eval's team, so check each selected document before applying it.

### Upload a document

1. Open **Red Team → Grading Guidelines** and select **Upload Grading Guideline**.
2. Enter a name and upload a PDF, TXT, or Markdown file, or paste text into **Document Text**. PDF files can be up to 10 MB.
3. Review the extracted text, then select **Upload**. Open the saved guideline to inspect **Document Content** or download the saved text.

Use a PDF with extractable text. If the preview is empty or incomplete, paste the text directly or upload a text file. Uploading a document does not change existing results.

### Apply guidelines to results

On-prem review requires a configured **Agent Provider**. Ask an administrator to open **Red Team Providers** from the profile menu, then select **Agent Provider** in the settings sidebar (`/server/edit/agentProvider`).

1. Open the red team eval's results.
2. Select **Apply Grading Guidelines**.
3. Review the selected documents. All guidelines shown in the dialog are selected initially; clear any that should not apply. If an expected guideline is missing, check that it belongs to your default team.
4. Confirm the selected guidelines and follow the progress in the results view.

[![Apply Grading Guidelines dialog with refund and identity-verification documents selected](/img/enterprise-docs/customization-guidelines.png)](/img/enterprise-docs/customization-guidelines.png)

This reviews saved responses, without sending new probes to the target. It reviews all FAIL results in the eval, rather than only the rows currently visible through a filter. A failure can be confirmed or revised to PASS; a revised result receives a passing score and a review reason.

:::note

Applying guidelines changes saved results. Reapplying them replaces previous guideline-review verdicts and revisits results that were previously revised to PASS. Review the explanations before using the updated results in a report.

:::

You can apply a saved guideline as soon as its document text is available. For guidance and examples applied during ordinary grading, see [Configuring the Grader](/docs/red-team/troubleshooting/grading-results/).

## Severity overrides

Use severity overrides when a plugin's default risk level does not match your application. For example, a team might classify unauthorized financial commitments as critical for a customer-facing purchasing assistant.

1. Open **Red Team → Plugins**, select **Severity Overrides** in the sidebar, and create an override. Enter a name and optional description.
2. Change at least one plugin's severity in the table, then save.
3. Open the target's **Plugin Severities** page and choose the set under **Selected severities**. The selection saves automatically.

[![Target Plugin Severities page showing the selected customer-support severity set and its customized risk levels](/img/enterprise-docs/customization-severities.png)](/img/enterprise-docs/customization-severities.png)

This example assigns **Support risk levels** to the target, with direct PII exposure classified as **Critical**.

A set belongs to a team. Editing a set affects future scans that load it; check the associated targets before changing it.

For CLI generation, use a saved Enterprise target provider (`promptfoo://provider/<target-id>`), including for on-prem targets. With a single saved target provider, its selected set's entries override severities configured for the same plugins in the scan. Plugins without an entry keep their configured severity or the Promptfoo default. Select **Promptfoo Defaults** on the target to remove its association with the set.

For CLI configs with multiple targets, severity lookup uses only the first provider. If it is a saved target provider, its overrides apply to the shared plugin list for every target in the scan. Generate each target separately when targets need different severity sets.

Severity controls risk classification, not whether an attack passes or fails. Saving an override does not regrade existing results. To change an existing finding, use its severity control in [Findings and Reports](./findings.md#viewing-vulnerabilities).

## Check your configuration

- If a library policy is missing, check the active team and whether the owning team shared it.
- If **Apply Grading Guidelines** is missing, check the Agent Provider and your eval permissions.
- If a severity override has no effect, check that the target selects it and generate a new scan; an existing test file retains its saved severities.
- Local providers using `config.linkedTargetId` do not load the linked target's severity set during CLI generation. Use the saved target provider directly to load the set, or [configure plugin severities explicitly](/docs/red-team/configuration/#severity-levels) for the local provider.
