# Scoped cloud SDK credentials

Evaluation environment files are scoped to their invocation. AWS, Google and Azure SDKs receive the effective credential inputs through constructor options; evaluation setup does not copy them into `process.env`. Provider configuration and the public per-key environment precedence remain unchanged.

An undefined value in a higher-priority environment layer leaves a lower-priority value intact. Explicit empty strings still clear selected values. SDK credential options and cache identity selection use the same merged layers.

AWS forwards static credentials, profile selection, shared/config file locations and web identity options. Without scoped credential inputs, the SDK retains its normal ambient discovery chain. Bedrock preserves explicit key-pair, bearer-token and configured-profile precedence. Agents and Knowledge Bases retain their SigV4 discovery behavior. Clearing a host Bedrock bearer token through an invocation environment forwards the SDK's empty-token option, so it cannot restore the host token; explicit credentials and selected SigV4 profiles retain their precedence.

Nova Reel and Luma async video requests keep the SDK's existing bearer-first ordering. File/suite bearer values, including empty masks, are passed to that SDK path. A configured or effective environment bearer bypasses the configured SSO profile, as it did at release; start, poll and S3 download clients still receive scoped IAM keys, environment profiles and file selectors. Provider-only bearer fields retain their pre-existing behavior. Knowledge Base request handlers retain their transport/proxy setup and cannot overwrite a selected explicit key-pair signature with a bearer header.

Agents, Knowledge Bases and async media clients share that released IAM selection. Credential resolution, SDK profile options and Agent cache identity derive from the same selected configuration; a bypassed configured profile cannot reappear through a separate SDK option. Their command-specific token handling remains separate.

Nova Sonic keeps its separate SDK discovery path: previously ignored configured credentials/profile/API keys and provider-only bearer fields stay ignored, while scoped AWS environment inputs reach the bidirectional command. This preserves valid released SigV4 calls. The SDK's ambient bearer selection remains unchanged, including its service limitation: [AWS requires standard credentials for bidirectional streaming](https://docs.aws.amazon.com/bedrock/latest/userguide/models-api-compatibility.html).

Scoped role profiles retain their environment source credentials, and nested SSO profiles retain selected shared/config files. A narrow adapter uses exported SDK package entrypoints for INI parsing, ordinary profile resolution, SSO and STS; it resolves them through the installed optional AWS client's dependency graph. Some exports are marked internal by the SDK, so SDK upgrades must retain the actual profile-chain regression tests. No private distribution paths or separately installed transitive dependencies are required.

Adapted profiles retain the SDK's post-INI process, web-identity and remote credential fallback, using the SDK's unavailable-versus-terminal error classification. Missing effective environment keys can continue to a later provider; terminal STS, SSO or MFA errors stop. This bounded tail never restarts host environment/profile discovery and retains caller context and native credential caching. Its provider order is an additional SDK maintenance boundary covered by actual fallback and refresh tests. Newly scoped profile cache namespaces also include effective web-identity fallback role selectors and token-file revisions; legacy ambient keys are unchanged.

Partial or empty static credential inputs retain SDK file-based discovery when no complete effective key pair is available. Selecting the effective or default profile prevents cleared host keys from reappearing; roles that explicitly use an environment credential source require a complete tuple to assume the role, while unavailable sources retain native fallback. Complete ambient keys retain priority over file-only overrides when no profile is selected. Empty shared/config filenames select the SDK's standard home files, and `~/` paths use the same home resolution for SDK calls and cache metadata. A cleared profile selects effective static keys first, then the default shared-file profile.

Google forwards ADC filenames, project and quota-project settings while retaining explicit configured credentials and API-key routing. Azure forwards service principals, certificate and workload identity files, and managed identity selectors while retaining the ambient default credential chain when no scoped identity is selected. The process-level `AZURE_TOKEN_CREDENTIALS` selector continues to control which SDK credential modes are eligible; developer/plugin chains and selector validation stay with the SDK. Invocation-specific overrides of that selector are outside this handoff. Partial identities retain SDK fallback; scoped tenant IDs are applied only to complete principal/workload identities so developer fallbacks retain their logged-in tenant selection.

Azure's existing environment username/password mode retains its position after client-secret and certificate credentials, before workload identity. Effective `AZURE_USERNAME` and `AZURE_PASSWORD` inputs are forwarded with the selected tenant/client; authentication errors remain fatal as they are in the SDK's environment credential. Scoped username identities include the public username in their cache namespace, without storing or hashing passwords. An unchanged ambient configuration keeps its existing cache key.

For complete scoped workload identities, a narrow adapter reads and copies Azure Identity 4's private `_sources` array after checking the SDK major and production credential layout. It binds the workload credential and the managed-identity token-exchange retry to the selected file and principal, then retains the SDK-created developer/Broker sources and ordering. The public `ChainedTokenCredential` preserves runtime fallback on unavailable credentials. Unknown layouts fail with an actionable error instead of retrying host credentials. This private layout and the managed token-exchange behavior are maintenance dependencies; actual SDK counterfactual tests cover selectors, constructor/runtime failures, error types, request options and conflicting host identities. The current fixture uses Azure Identity 4.13.3; compatible minor releases are accepted by the layout guard.

Synchronous scoped environment-credential constructor failures retain the SDK's remaining credential chain. The same guarded source-list adapter removes the host environment mode so an invalid scoped principal cannot silently select a valid host principal. Existing scoped workload handling runs before this fallback, and token-acquisition errors retain their original fatal behavior.

SDK clients are owned by both an environment and an evaluation resource lifetime. Concurrent evaluations can reuse a provider object without sharing credentials or closing one another's resources. Caller-injected clients remain caller-owned, including the quota project on a supplied Google auth client. Standalone SDK consumers outside an evaluation keep provider-owned lifetimes; the registry does not retain those clients.

Response caches retain existing ambient/configured keys. Newly scoped identities use stable public selectors, such as AWS access-key IDs or Azure tenant/client IDs; file-backed identities include file revision metadata. A scoped web-identity token file includes its effective public role ARN, even when that selector is inherited from the host. Identical selectors and files retain cache reuse across processes. New scoped namespaces also distinguish unavailable or invalid credentials from complete role/principal credentials, because the SDK may select a different fallback identity. Foundry includes the native credential selector and explicit authority overrides in that partition. Secret rotation within the same complete principal retains cache reuse; no new persistent cache fingerprint is derived from a raw secret.

A provider-only Bedrock bearer token has no public identity selector, so its additional cache namespace is held in memory and cannot be reused across processes. Knowledge Base responses use this same namespace only when that new bearer source is selected. Bearer tokens from configuration, suite environments and environment files retain each provider's existing cache format. New client lifetimes select the current credential-file revision. Rotate credential files between evaluations: existing SDK clients retain their original cache partition and follow the SDK's own credential memoization or refresh schedule. Unchanged metadata is treated as the same file revision.

Empty Azure settings remain harmless when they have no host value to mask. If the selected SDK credential chain would restore a nonblank host value that an invocation explicitly cleared, evaluation reports the masked setting. Supply an explicit scoped identity or remove that host setting before evaluating. Higher-priority secret, certificate or workload identities do not consult cleared lower-priority file settings.

Google ADC environment files are validated through the SDK constructor, preserving configured client options and binding project discovery to the selected client. ADC keeps the SDK's environment quota precedence over client options; an empty quota environment setting retains the credential's quota fallback, or the client option for metadata/API-key clients without credential JSON. Explicit credential JSON/key files and caller-owned auth clients retain their quota behavior. Explicitly configured SDK API keys, auth clients, credentials and key files retain their authentication priority. A blank ADC placeholder continues normal discovery when there is no host ADC filename to restore; clearing a nonblank host ADC filename reports an actionable error.

Blank Google project placeholders retain a configured `googleAuthOptions.projectId`, then normal SDK project discovery. An invocation that clears a nonblank host project can still use an unmasked SDK project alias or the selected credential file project; set an explicit project or remove the host project setting to enable other discovery sources for that case.
